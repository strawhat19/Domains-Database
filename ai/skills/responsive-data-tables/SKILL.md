# Responsive Data Tables

Apply this pattern when creating or changing a table, record list or long horizontal data row, including nested detail tables and account/report records. Preserve the destination's framework, palette, fonts, data meanings and permitted actions. A focused adoption affects the requested views; it does not authorize a project-wide rewrite or new backend resources. Respect an explicitly requested fixed table/comparison layout.

## Adopt The Pattern

1. Inspect the existing row renderer, column definitions, data/service boundary, container, toolbar, footer, settings and saved preferences. Identify required identity fields, primary values/status, related secondary groups, actions and real search/filter/sort coverage. Distinguish working controls from unused helpers or visual placeholders.
2. Use one stable column/record model for wide rows, compressed rows and mobile cards. Derive visible fields, their order, labels, formatting, sorting and eligibility from that model. A layout change preserves the query/result set, value meanings and permissions; do not substitute different records, invent values or silently discard data. Keep app-specific schemas, breakpoints and implementation evidence outside `ai/`.
3. Fill the actual available table container on large screens. Use the horizontal budget to show useful data in aligned rows, with header/body sharing the same column geometry. Measure around sidebars, detail panes and existing page gutters; do not make unrelated public pages full-width. Prefer designated flexible columns to an unused blank strip or a fixed narrow table.
4. Compress progressively as that container narrows: reduce expendable padding/gaps, use compact formatting without changing precision/meaning, wrap supporting text and arrange related metrics in smaller grids. Keep identity, primary values, status and actions legible; do not solve width pressure by scaling the whole row or making every value tiny.
5. When a useful horizontal row no longer fits, reflow it into a compact record card. Keep identity and the primary value/status prominent, related fields labelled, and the same permitted actions reachable. Use two or more metric columns while they fit rather than stacking every field into a tall card. Preserve optional-field choices and ordering. An intentional disclosure or locally scrollable comparison group can retain dense secondary data; expose it clearly instead of hiding it at a breakpoint.
6. Drive these modes from measured container width, declared minimum sizes and content needs, with web container queries/observers or native `onLayout`. Choose destination-specific thresholds. Retain saved desktop widths through mobile mode and restore them when space returns. Resizing the browser must not clear preferences or change selected records, filters, sort, page, expansion, row drafts, validation or pending operations.
7. Keep filters and search above the data, settings/actions in their existing toolbar, and existing status/paging/source footers in place. Compact the surrounding chrome so the data receives most of the remaining height. Prefer a short wrapping toolbar or horizontally scrollable filter rail with a discoverable overflow edge; keep search usable and important actions/settings visible. Menus must remain within the viewport and reposition with their anchors rather than being clipped by the rail. Preserve footer information and required links while adapting its spacing.
8. Give data-rich tables one accessible **Table Settings** control. Reuse the app's settings glyph, labelled square actions and reduced-motion treatment. Include applicable column visibility, order, compact density, field labels, resize/Fit/Stretch and reset controls. Required identity/action fields stay available. Reordering has keyboard/touch alternatives to drag; unavailable capabilities are disabled with an honest reason or omitted when irrelevant. A small read-only list need not acquire meaningless customization controls.
9. Keep the sizing actions distinct: **Resize** changes a chosen column's preferred width; **Fit Columns To Contents** measures useful rendered labels/data within bounds; **Stretch** assigns spare horizontal space to selected eligible columns. Reset restores table preferences only. Follow the sizing and state contract in [implementation.md](references/implementation.md) when implementing or changing these behaviors; do not replace them with equally sized columns or a canned width.
10. Keep table behavior usable across layouts: genuine search/clear, filters and active chips, stable sorting and direction, group headings, row selection, expansion and permitted actions. Label loaded-page filtering/sorting separately from server-wide queries. Settings affect the actual renderer and shared state; confirm persistent saves through the existing adapter and preserve the last confirmed state after failure.
11. Preserve accessible structure, descriptive record-based IDs, labels/units, status text and visible focus. Use semantic tables where the content is tabular; card renderers can use lists/articles and labelled field groups. If a renderer uses ARIA table semantics, keep valid row/cell relationships and meaningful labels in every mode. A visually hidden desktop heading is not a substitute for readable mobile field labels. Keep essential action targets usable on touch, typically at least 44 units, while compact visual controls may remain smaller within their hit areas.
12. Share normalized records, layout decisions and preferences across web/native; translate rendering and interaction to supported platform primitives. Do not claim native resizing, fit measurement, sticky columns or drag support from a web implementation. Provide real supported controls or explicitly identify the remaining difference. Keep avatars, source icons, statuses, units and null/error states consistent in rows and cards.

For Profile/Admin/Dashboard, also follow [the account layout](../admin/layout.md) for shell geometry, action/status cells, editors and paging. [User Identity](../user-identity/SKILL.md) owns displayed user identity; existing database/API/access contracts remain authoritative. This skill owns responsive row/table behavior, rather than changing those policies.

## Review And Handoff

Read [the review matrix](references/implementation.md#review-matrix) when adopting the pattern. Check source mappings first and follow `AGENTS.md` for any tests, builds, UI checks, commits or deployment. Do not run unrequested checks. Report implemented behavior, native differences, actual save/source boundaries and what was or was not validated; source inspection alone does not prove responsive rendering or cloud persistence.
