# Plan Catalog

Admin Plans manages the app’s persisted public pricing catalog. Active Owner, Admin, and legacy Administrator accounts can create plans, edit their catalog details, change Active/Inactive status, and Archive. Developer and Subscriber accounts can browse active plans but cannot manage or read inactive catalog entries.

Configure the app’s Firebase environment and deploy this repository’s `firestore.rules` and `firestore.indexes.json` before using the connected catalog. The public query needs the `plans` composite index on `active`, ascending `displayOrder`, and ascending `number`. Admin paging uses the descending `number` index. No rule, index, project, or document is deployed by this source change.

Each record contains exactly `id`, `type`, `number`, `name`, `slug`, `description`, `features`, `currency`, `priceCents`, `billingInterval`, `active`, `displayOrder`, `created`, and `updated`. IDs use the shared `Plan_Number_Name_Date_UUID` helper. `counters/plans` allocates a matching integer number atomically with each new record; `planSlugs` reserves the unique lowercase hyphen slug in the same transaction. Names are limited to 100 characters, slugs to 100, descriptions to 2,000, and feature lists to 30 entries of 200 characters each. Prices and display order use nonnegative safe integers. Currency supports USD, EUR, GBP, CAD, AUD, and BDT; billing intervals are month, year, and one-time. Cloud writes use server timestamps, normalized to ISO strings at the service boundary.

Legacy `highlighted` booleans are accepted only when reading saved catalogs. Current models and newly saved records omit the field; cloud edits and status changes remove it without changing plan identity, slugs, ranks, or account entitlements. Local catalog writes serialize the same current shape. No automatic migration or cloud cleanup runs on page load.

Identity, number, slug, and creation time remain stable after creation. Archive sets the persisted active flag to false and preserves the record and slug reservation; the service and Firestore rules do not physically delete plans. A plan can later be reactivated through the normal status action. Catalog edits and archiving never change `User.plan`, roles, subscriptions, payments, account limits, or entitlements. Existing Free/Pro account values remain independent of the catalog. No checkout, provider price ID, billing integration, or paid entitlement grant is implemented by this catalog.

The public realtime subscription returns up to 100 active plans, ordered by display order and then number. Admin management returns 50-record numbered cursor pages, newest first. Cloud subscriptions wait for a server-confirmed snapshot instead of showing pending writes or cached data as a successful live load. Empty catalogs stay empty, and plans are created manually through Admin; no sample seed or error fallback repopulates the database.

The existing explicit local mode stores a versioned catalog snapshot through the shared storage adapter and retains monotonically increasing numbers and stable slugs. It is device-local, not shared production pricing. A configured Firebase failure never switches a plan operation to local storage. Missing configuration, denied roles, missing indexes, unreadable saved records, and connection failures are reported so the UI can retain drafts and offer retry.

Consumers use `plansAPI` from `src/api/plans.ts`. It exposes `createPlan`, `updatePlan`, `setPlanActive`, `archivePlan`, `getPlansPage`, `subscribePlansPage`, and `subscribePublishedPlans`, plus the shared input types, supported currency/interval lists, limits, and source label. Every mutation derives its actor from the current session; connected mutations read the authoritative account role inside the transaction. All persistence and public read behavior is shared across web and native consumers.
