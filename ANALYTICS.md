# Domains Database Admin Setup

The admin area uses this app's existing Firebase project and Expo server routes. Copying `ai/` and `AGENTS.md` to another repository supplies implementation guidance; each app still needs its own Firebase/Vercel configuration, provider enablement, access bootstrap, and reviewed rules.

1. Set the public Firebase web configuration from `.env.example` in the ignored local environment and deployment build environment. Enable Google and any requested email/password provider in Firebase Authentication, then add the local and custom production domains to Authorized Domains. New accounts remain private Subscribers. Registrar credentials remain in private account connection records.
2. Review and publish `firestore.rules` and `firestore.indexes.json` through the existing Firebase setup. The new domain collection group query needs the descending `number` collection group index. Rules permit bounded account/domain inspection for Owner, Admin, and legacy Administrator; Developer receives the registration counter and technical reports without private account or portfolio access.
3. Bootstrap an Owner through a trusted Firebase Console or privileged administration process after verifying the intended account. Follow `identities/{firebase_uid}.id` to its app-owned `users/{id}` record and set both `role: Owner` and `roles: [Owner]`, retaining the existing ID/number/UID. Do not grant Owner to the first signup automatically. After bootstrap, the Owner can assign roles in Admin > Users.
4. Enable Vercel Web Analytics for the deployed project. The existing `@vercel/analytics` web integration collects page views; collecting events and reading reports are separate capabilities. Configure the private `VERCEL_ANALYTICS_TOKEN` and `VERCEL_ANALYTICS_PROJECT_ID` for reporting, plus `VERCEL_ANALYTICS_TEAM_ID` for team projects. Existing private `VERCEL_API_TOKEN`, `VERCEL_PROJECT_ID`, and `VERCEL_TEAM_ID` serve as fallbacks. Keep these values out of public build variables, account forms, logs, and User records. Restart the local server after environment changes.
5. Observability requires the configured team, project, and token to have access to Observability Plus. The adapter discovers available metric names, aggregations, and dimensions before querying. Unsupported measurements remain unavailable; missing plan/access returns a configuration message. No purchase, deployment, secret change, or Firebase rules publication is performed by this implementation.

| Capability | Subscriber | Developer | Admin / Administrator | Owner |
| --- | --- | --- | --- | --- |
| Own profile and private connections | Yes | Yes | Yes | Yes |
| Overview registration counter | No | Yes | Yes | Yes |
| Vercel traffic and observability | No | Yes | Yes | Yes |
| Bounded user/domain inspection | No | No | Yes | Yes |
| Change ordinary account status | No | No | Yes | Yes |
| Change elevated account status | No | No | No | Yes |
| Assign roles | No | No | No | Yes |
| Read another account's saved credentials | No | No | No | No |

User role/status writes use a Firestore transaction with an atomic `counters/adminAudits` counter and immutable `AdminAudit_Number_UserAccess_Date_UUID` record. Rules require the audit and user changes together, preserve identity fields, and reject self-access changes. Admins cannot change Owner, Admin, Administrator, or Developer status. A second active Owner must change an Owner's own access. Account deactivation disables the app's private data and reporting access; it does not administratively disable the underlying Firebase Auth user.

The realtime overview listens to the latest 100 account records and up to 500 domain documents; a 101st/501st document signals incomplete coverage. Account/domain cards and charts describe the loaded subset. `Accounts Registered` comes from the monotonic signup counter and counts accounts allocated historically, including any records subsequently removed through trusted administration. It is not a current total or online-user metric. The user management table pages 50 records at a time. Developer overview contains no account records or domain details. Local mode uses existing local Owner account records and makes cloud access management unavailable.

`GET /api/admin/analytics?days=7|30|90` and `GET /api/admin/observability?hours=24|168|720` verify a Firebase ID token with Identity Toolkit, resolve its immutable app identity, and check its current active Firestore role before returning any cached provider report. Report responses are private/no-store. Provider results use bounded requests and a five-minute process cache keyed by token hash, team, project, and query; displayed fetch/cache timestamps describe this delay. Firestore application data remains realtime. Technical reports currently require the web dashboard; native applications show an explicit web-reporting message.

Traffic reports also support `from=YYYY-MM-DD&to=YYYY-MM-DD` instead of `days`, with optional `country`, `device`, `path`, and `referrer` segments. The server rejects unknown or repeated parameters, invalid segment values, future dates, ranges longer than 90 days, and date ranges whose preceding comparison period extends beyond the last year. All queries retain the configured production project and authenticated admin scope. The compact overview has Overview, Daily, Countries, Sources, Pages, and Devices tabs, chart/list displays, comparison and inspection controls, and a dates/segments drawer. Full analytics exposes the same date and segment filters, interactive daily chart, and breakdown rankings. JSON exports contain the displayed provider report.

Traffic totals use an aggregate query grouped by production environment across the complete selected period, with an equal preceding comparison period. Daily visitor counts are not summed into period unique visitors. The trend and top pages, countries, devices, and referrers use separate bounded aggregates. Empty successful provider results are valid; unconfigured or failed reports never become invented traffic.

The [public Web Analytics guide](https://vercel.com/docs/analytics/web-analytics-api) and [aggregate REST reference](https://vercel.com/docs/rest-api/web-analytics/aggregates-page-views) document the traffic API. The observability adapter follows the canonical `/metrics/v1` contract used by the official Vercel CLI: [catalog implementation](https://github.com/vercel/vercel/blob/main/packages/cli/src/commands/metrics/schema-api.ts), [query implementation](https://github.com/vercel/vercel/blob/main/packages/cli/src/commands/metrics/query.ts), and [request/response types](https://github.com/vercel/vercel/blob/main/packages/cli/src/commands/metrics/types.ts), reviewed October 11, 2026. That source-backed contract can evolve; retain capability discovery and recheck the official source when upgrading. [Vercel metrics documentation](https://vercel.com/docs/cli/metrics) describes current metric names and plan requirements. If the canonical API becomes unavailable, use a trusted scheduled CLI export or supported Drains aggregate rather than browser scraping or guessed endpoints.

No build, test, browser check, commit, deployment, rule publication, Owner promotion, or provider connection was run as part of this change. Review the source and configuration before enabling it.
