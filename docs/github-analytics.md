# GitHub Repository Analytics

The GitHub tab on Analytics reports only `strawhat19/Domains-Database`, matching this app’s repository. Health remains in its separate existing admin menu. The private `GET /api/admin/github` endpoint verifies the Firebase token and current active Owner capability with `requireAnalyticsAdmin` before accessing either provider data or an in-memory cache. Report responses use `Cache-Control: private, no-store` and vary by Authorization. Query parameters cannot select a different repository or upstream destination.

## Server Setup

Public repository metadata, commits, published releases and languages can load without a GitHub credential, subject to GitHub’s unauthenticated API limit. Repository traffic requires a server-only `GITHUB_ANALYTICS_TOKEN`. This adapter accepts an existing classic PAT or a fine-grained PAT as a bearer token; there is no fine-grained-only restriction in its code. An authorized classic token with `repo` scope covers the repository reads; a fine-grained token needs Metadata read, Contents read and Administration read permissions. GitHub also requires the personal token's actor to have repository write access for traffic. A configured invalid or expired token produces an explicit failure rather than silently falling back to a different identity. The adapter does not automatically read generic `GITHUB_TOKEN`, Git credentials, connected-app credentials or a visitor’s Profile Connections.

Add the actual secret in the deployment’s private server environment and restart/redeploy its Node server as appropriate. Do not prefix it with `EXPO_PUBLIC_`, write it into Firestore, or return it to the browser/native app. The existing Firebase configuration, permitted Owner account and deployed server routes must also be available. Reporting is currently supported in the web dashboard; native views show an explicit web-reporting state.

The initial source implementation did not configure a token or prove hosted access. Subsequent authorized local setup copied the existing GITHUB_CLASSIC_API_TOKEN into GITHUB_ANALYTICS_TOKEN in this project's ignored, untracked .env, preserving the source entry and other values. This establishes local credential configuration only; the server still needs to load it after restart. A subsequent read-only diagnostic authenticated successfully to the views/clones provider endpoints; the app report endpoint, hosted secret configuration and deployment remain unverified.

### Setup For Domains-Database

1. Reuse your existing authorized classic PAT if it has the repository scopes/access needed for these reads. A classic PAT with `repo` scope works for the implemented repository reads, subject to organization restrictions and any required SSO authorization. Save its existing secret value under `GITHUB_ANALYTICS_TOKEN`; no new fine-grained token or app code change is required. The reporting adapter uses read-only requests even though a classic `repo` token has broader privileges.
2. If you choose a new fine-grained token, open [token settings](https://github.com/settings/personal-access-tokens), choose an expiration, select resource owner **strawhat19**, and choose **Only Select Repositories → Domains-Database**. You can select other intended repositories under that owner on the same token. Grant **Administration: Read-Only**, **Contents: Read-Only** and **Metadata: Read-Only** (Metadata may already be included). The GitHub user issuing either token type must have write access to this repository for traffic. Complete organization approval when applicable. This step is optional when reusing a suitable token.
3. In the Vercel project hosting this app, open **Environment Variables** and add **GITHUB_ANALYTICS_TOKEN** with the generated token as a private **Secret** where supported. Select **Production** for the live app; add Preview or Development only where that environment should read the repository's private traffic. Save it at the project level.
4. Create a new deployment for the selected environment so its server receives the value. Saving a variable does not update an existing Vercel deployment. This app's Expo server output is served through `api/index.ts` with `dist/server/**`; its protected report route is `app/api/admin/github+api.ts`.
5. For local web development, put `GITHUB_ANALYTICS_TOKEN` in this repository's ignored `.env.local`, then restart the local web server that serves API routes. Use the same variable name without an `EXPO_PUBLIC_` prefix. Editing a local file does not configure the hosted deployment.
6. After the intended deployment/restart, sign in as an active app Owner, open **Analytics → GitHub**, and choose **Refresh**. Review the views/clones section statuses and fetched time. A real zero response is valid; a missing or denied response remains unavailable. These are manual setup/review steps, not checks performed by this documentation update.

The token belongs in the app's server environment. A GitHub Actions secret, GitHub/Vercel Git connection, local Git login or connected Codex GitHub account does not automatically populate it. Never paste the token into chat, commit it, or add it to public/client configuration. [GitHub token instructions](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [traffic permissions](https://docs.github.com/en/rest/metrics/traffic), [Vercel environment setup](https://vercel.com/docs/environment-variables/managing-environment-variables)

### Repeat For Another Project

Use the same `GITHUB_ANALYTICS_TOKEN` variable name in that app's hosting project and required environments. You can reuse one authorized classic PAT across the repositories it can access, or one fine-grained PAT covering several intended repositories under a single owner. Separate per-app tokens are optional when independent rotation/revocation is preferred. Keep the actual token value private in each intended server environment.

The current adapter fixes `repositoryOwner` and `repositoryName` in `src/server/admin/github.ts` to `strawhat19` and `Domains-Database`. Changing the token alone does not change the reported repository. A destination copying this implementation must update that server-owned repository binding and its app-specific User-Agent/report/export labels, retain the current Owner-protected API boundary and supported server runtime, and document its own setup outside `ai/`. This adapter does not currently read repository owner/name environment variables. Use [the reusable GitHub contract](../ai/skills/admin/references/github.md) and [the adoption prompt](../ai/adoption.md#github-repository-analytics-prompt) for the focused implementation in another app.

### Troubleshooting The Connection Message

`Repository Traffic Requires A Server Connection With GitHub Administration Read Access` is returned before the provider request when this app's running server sees an empty `GITHUB_ANALYTICS_TOKEN`. Check the exact hosting project/environment and whether the latest deployment or local server restart loaded the value. This message does not by itself mean that a configured token was denied by GitHub.

An invalid/expired-token message requires credential replacement. For access denied, check classic scopes/organization SSO or fine-grained repository selection/Administration read, plus the token user's repository write access and organization policy. A repository-unavailable message also requires checking the fixed server binding. App sign-in/Owner errors come from the app's own account boundary. Rate-limit and partial responses retain their actual section status; public metadata loading alone does not prove private traffic access.

`GitHub Returned Unsupported Traffic Buckets` came from an overly strict local retention cutoff: the adapter rejected a valid returned day older than the server's UTC today minus 14 days. A read-only diagnostic using this project's configured credential returned HTTP 200 for both views and clones, with valid UTC timestamps, integer counts and unique dates; GitHub's supplied snapshot extended one day beyond that calculated cutoff. The parser now preserves those supplied dates while retaining timestamp/midnight, future-date, count and duplicate checks. Selected-range intersection still applies, missing days stay null, and section coverage states the latest supplied day when the snapshot lags. The app endpoint and browser rendering have not been checked after the source fix.

## Metrics And Coverage

The endpoint accepts `days=7|14|30|90` (default 7). Commit selection uses the current default branch and a UTC range ending at the request time. Its daily trend and contributor rankings cover the selected period; commit totals require complete pagination. The latest 20 commits and top 10 GitHub usernames are shown. Unlinked authors are combined into one named bucket; commit author email addresses and raw provider user records are never returned.

Commits are limited to ten pages of 100 records. If a later page fails, times out, is malformed, or exceeds the page limit, successfully normalized recent commits and contributor counts remain available with partial coverage. The full commit total and daily commit trend become null because the selected interval is incomplete. Contributor counts in that case describe loaded commits only.

GitHub’s views/clones endpoint retains a rolling 14-day window, which can touch 15 UTC dates. Traffic totals use the selected period intersected with returned retention. Daily counts may be added for a shortened window only when all provider daily counts reconcile with the provider total. Exact period unique visitors/cloners are used only when the whole provider window is included; a shortened window returns null uniques. Daily unique counts are never summed into period uniques. Missing daily buckets and dates outside retention remain null in the trend. No historical traffic archive or scheduled ingestion is added.

Release coverage is separate from the selected commit period: up to three pages of 100 release records are read across repository history, draft releases are excluded, and the latest 20 published releases are displayed. An incomplete page set or malformed data produces a null full release total and explicit coverage. Regular Git tags without a published release are excluded. Asset downloads sum the lifetime `download_count` values on the assets returned for each release; they are not downloads during the selected period and do not include automatically generated source archives.

Stars, forks, subscribers/watchers, languages and open issues plus pull requests are current repository snapshots. Language values are bytes returned by GitHub, not lines of code. Metadata is required to establish the fixed repository and default branch; failures in other metric sections retain successful sections. Unavailable metrics are null, with per-section status and safe messages for denied access, rate limits, unsupported responses and timeouts.

## Leading Icons And Images

GitHub reporting uses the Traffic tab's leading-identity treatment on web and native: a local GitHub mark for the repository, matching metric and chart-control glyphs, date and channel icons, language marks beside ranking labels, contributor avatars, and tag/commit/download visuals in release and commit rows. Language percentages and slim bars retain their actual byte proportions and matching color keys. Text labels, values, nulls and coverage messages remain readable alongside the artwork.

The allowlisted 16-language catalog lives in `public/analytics/languages`, with identical portable artwork in `ai/skills/admin/assets/analytics/languages`. Pinned sources, upstream notices and applicable individual artwork licenses are retained. Unknown or omitted language marks use a code glyph. Native uses literal bundled asset mappings and its existing image/vector renderers.

Contributor `avatarUrl` is optional and comes only from the existing GitHub commit response's linked author. The adapter and renderer restrict it to HTTPS numeric user/app image paths on `avatars.githubusercontent.com`; credentials and arbitrary image hosts are excluded. No extra contributor API request or private app profile lookup is added. Missing, rejected or failed avatars use initials/person fallback, and failure state resets with identity changes. Adjacent icons and images are decorative for accessibility. JSON export now includes the optional public avatar URL with the existing report fields.

This visual change is source-reviewed only; no build, compiler, UI/browser/native-device or live provider check was run for it. Native's existing authenticated report transport limitation still applies.

## Request Limits And Caching

Each report has a 20-second provider deadline and each upstream request an 8-second timeout. The existing bounded JSON reader rejects responses exceeding 3 MB. A report runs at most three section workers, each paginating sequentially; at most two reports run per server process, giving at most six concurrent upstream requests. The existing admin handler also caps concurrent report requests at eight and independently rechecks current account access.

Four supported periods use a five-minute, per-process report cache. Concurrent requests for one period share an in-flight operation. `refresh=1` bypasses a completed cache entry while retaining in-flight deduplication. Token changes invalidate completed cache entries; results fetched under the old credential cannot populate the new credential’s cache. Serverless instances have independent caches and limits. No persisted provider data, background polling, cloud resource or deployment is created.
